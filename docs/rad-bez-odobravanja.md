# Рад без одобравања

## Зашто постоји

Ланац одобравања претпоставља да шефови одељења и директор редовно потписују.
Кад то изостане, извештај запосленог остаје у `SUBMITTED`, а верзија документа
у `na_odobrenju` — посао стоји због туђе инерције, а запослени који је свој део
урадио на време изгледа као да није.

Два прекидача гасе захтев за потписом, свако за свој ток.

## Шта гашење НЕ ради

**Не проглашава ништа одобреним.** То је најважније правило целе измене.

| | одобрено | без одобравања |
|---|---|---|
| статус (радне листе) | `APPROVED` | `BEZ_ODOBRENJA` |
| статус (документи) | `odobreno` | `bez_odobrenja` |
| `is_verified` | `TRUE` | `FALSE` |
| `head_verified_by` / `director_verified_by` | попуњено | **NULL** |
| `reviewed_by_email` (документ) | попуњено | **NULL** |
| ознака у приказу | зелено „Одобрено" | сиво „Без одобравања" |

Годину дана касније нико неће памтити када је прекидач био угашен. Зато статус
мора сам да каже. Исти разлог зашто миграција 040 има посебан траг за
административно одобрење — само јаче: ове није потписао нико.

## Где се пали и гаси

**Админ панел** → Систем → Подешавања → картица „Одобравање". Два прекидача.
Пре промене се прикаже колико ставки тренутно чека, а потврда каже шта ће им
се десити. Промена важи одмах (кеш подешавања је 60 s).

**Командна линија** — исти механизам, за случај кад страница не ради:

```bash
python3 scripts/odobravanje.py stanje
python3 scripts/odobravanje.py iskljuci izvestaji            # dry-run
python3 scripts/odobravanje.py iskljuci izvestaji --execute
python3 scripts/odobravanje.py ukljuci dokumenti --execute
```

**Променљива окружења** — излаз у нужди, јача од базе:

```bash
MIS_ODOBRAVANJE_IZVESTAJA=0
MIS_ODOBRAVANJE_DOKUMENATA=0
```

Ако је преклоп постављен, картица у админ панелу то каже — дугме тамо неће
имати ефекта док се преклоп не уклони са сервера.

## Подразумевано је УКЉУЧЕНО

Нема подешавања, база пала, вредност бесмислена (`"možda"`, празан низ, број)
— све води у укључено. Контрола се гаси само изричитом одлуком, никад грешком.

Редослед: окружење → `system_settings` у бази → подразумевано укључено.

## Шта се дешава са затеченим

**Кад се гаси:** оно што чека прелази у завршено стање, уз ред у историји
(`timesheet_status_history`, односно `document_audit_log`) који каже зашто.

- радне листе: само `SUBMITTED`. `REJECTED` се не дира — те су враћене
  запосленом и он их поново подноси, тада већ по новом правилу.
- документи: најновија верзија на чекању по документу постаје важећа; старије
  верзије на чекању и раније важеће иду у архиву, да документ никад нема две
  важеће одједном.

**Кад се пали назад:** затворено остаје затворено. Враћање десетина листа у ред
за потпис недељама касније изненадило би и запослене и шефове. Ако баш треба,
админ враћа појединачну листу дугметом „Врати запосленом на измену".

## Шта се НЕ мења

Оперативни захтеви (`pending → in_review → approved`) имају свој ланац и овим
прекидачима се не дирају.

Већ одобрене листе и документи остају одобрени. Миграција 054 не мења ниједан
постојећи ред — само проширује дозвољене статусе.

## Провера да ово стварно ради

```bash
python3 -m pytest -q test_odobravanje_prekidac.py \
                     test_odobravanje_razresavanje.py \
                     test_odobravanje_ui.py
```

Тестови покривају и случајеве који су смисао ограде: пад базе не гаси контролу,
бесмислена вредност не гаси контролу, dry-run стварно ништа не мења, и
`BEZ_ODOBRENJA` се не сме наћи међу одобренима.
