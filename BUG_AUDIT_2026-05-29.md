### [C] Command injection: admin-entered password interpolated into python3 -c source
- **Location:** `museum_control_center.py:2325-2338`  ·  **module group:** control-center  ·  **category:** command-injection  ·  *confirmed by verifier*
- **What's wrong:** Verified at lines 2325-2332: hash_script = f'''...hasher.hash_password("{new_password}")...''' then subprocess.run(['python3','-c', hash_script]). new_password is admin-typed via simpledialog.askstring (2298) with zero validation. A password containing a double-quote, backslash or newline terminates the Python string literal and injects arbitrary code that runs with the app's privileges and sys.path including /home/aleksandarlukovic/MuseumInfoSystem (line 2327). The same admin-input vector is real in set_temporary_password (custom_pass at 2537, f-string'd at 2567). NOTE: the auditor also cited reset_and_show_password (2464-2469), but there new_password = self.generate_strong_password() (2460), whose alphabet is string.ascii_letters + string.digits + '!@#$%^&*()' (line 2627) — it contains no double-quote, backslash, or newline, so that specific call site cannot inject. The finding is still correct and critical for the two admin-input paths (reset_user_password, set_temporary_password).
- **Fix:** Stop templating the password into source. Pass it via argv and read sys.argv[1] inside the script, or pipe via subprocess stdin (input=new_password) and read sys.stdin. Even simpler: hash in-process by importing PasswordHasher directly instead of spawning python3 -c.

### [H] add_user never persists the new user to the database (silent data loss)
- **Location:** `employee_admin_views.py:69-87`  ·  **module group:** admin-users  ·  **category:** data-integrity  ·  *confirmed by verifier*
- **What's wrong:** Read handle_add_user end to end (lines 43-101): the only write is `employees[email] = {...}` (lines 69-78) into the dict returned by get_museum_employees(), which is the in-memory fallback cache MUSEUM_EMPLOYEES (app.py:1021-1032 via app_runtime_support.get_cached_value). ### [H] Bilja import-failure fallback is defeated by an unguarded `_bilja_db` reference, crashing app startup
- **Location:** `app.py:1197-1215, 1332`  ·  **module group:** app-core  ·  **category:** crash  ·  *confirmed by verifier*
- **What's wrong:** Verified directly from source. The name `_bilja_db` is bound ONLY inside the try block: line 1198 `import bilja_collections_db as _bilja_db`. The except branch (lines 1207-1215) logs a warning and assigns the six BILJA_*_DATABASE fallback dicts but NEVER binds `_bilja_db`. Then at line 1332, OUTSIDE any try/except, the module runs `for _bilja_key, _bilja_cfg in _bilja_db.COLLECTIONS.items():`. grep confirms `_bilja_db` appears only at lines 1198, 1200, 1332 — there is no other guard. The failure is concretely reachable: bilja_collections_db.py line 19 does `import psycopg` at module top level, so on any environment where psycopg is missing or import-time evaluation fails, line 1198 raises, the except branch runs without binding `_bilja_db`, and line 1332 raises `NameError: name '_bilja_db' is not defined`, propagating out of `import app` and aborting Flask startup. The except block's documented purpose (degrade gracefully to empty collections) is therefore defeated. Note: `_bilja_db.load_all()` itself (line 341-354 of bilja_collections_db.py) already swallows per-collection DB errors internally, so the most likely failure mode that triggers this is precisely an import-time failure, which is exactly the path that breaks.
- **Fix:** Set `_bilja_db = None` inside the except branch (after line 1208), then gate the registration loop: `for _bilja_key, _bilja_cfg in (getattr(_bilja_db, 'COLLECTIONS', {}) or {}).items():`. Alternatively move the loop (lines 1331-1341) inside the try block after `load_all()` succeeds.

### [H] Pooled DB connection leaked on any exception in chat_room functions
- **Location:** `chat_room.py:65-76, 164-274`  ·  **module group:** chat-qr  ·  **category:** resource-leak  ·  *confirmed by verifier*
- **What's wrong:** Confirmed. _get_db() (chat_room.py:65-76) returns get_postgres_connection(row_factory=dict_row). ### [H] SQL injection: email interpolated into psql UPDATE statements
- **Location:** `museum_control_center.py:2348-2360`  ·  **module group:** control-center  ·  **category:** sql-injection  ·  *confirmed by verifier*
- **What's wrong:** Verified: update_sql is built with f-strings (2348-2353) and run via psql -c (2355-2360). The genuinely injectable value is email (2353 WHERE email = '{email}'); the same unparameterized pattern recurs at force_password_change (2392), toggle_user_status (2429), reset_and_show_password (2486-2491) and set_temporary_password (2584-2589). This directly violates the explicit project rule 'No f-string SQL'.
